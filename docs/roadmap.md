# Этапы разработки и критерии готовности

Статус: план с отметками выполненных шагов; результаты первого запуска вынесены
в [отчёт](hardware-bringup.md). Ориентир — восемь недель
по 12–15 часов с изучением микроконтроллеров. Срок уточняется по фактическому
темпу; критерии качества не заменяются календарной датой.

## M1 — первый запуск, неделя 1

- [x] Активировать ESP-IDF v5.5.6, проверить версию.
- [x] Собрать официальный `hello_world` для `esp32` и запустить на своей плате.
- [ ] Создать минимальное приложение проекта с воспроизводимой сборкой.
- [ ] Вывести текст на OLED, прочитать две кнопки с подавлением дребезга.
- [ ] Записать схему подключения и инструкцию повторения.

Готово, когда новая сборка стартует на плате, а её UART-лог и схема позволяют
повторить результат. До первого запуска не требуется подключать OLED и кнопки.

## M2 — приём на одном канале, неделя 2

- [ ] Включить пассивный promiscuous mode без STA/AP-подключения.
- [ ] Реализовать фиксированный пул 64 × 512 байт и очередь индексов.
- [ ] Копировать данные в callback и обрабатывать вне задачи драйвера.
- [ ] Добавить статистику очереди и отдельные причины отказов.
- [ ] Искусственно замедлить обработку и проверить восстановление после перегрузки.

Готово, когда при заполнении очереди устройство считает локальные потери,
не блокирует Wi-Fi callback и продолжает работать после снятия нагрузки.

## M3 — парсер и точки доступа, неделя 3

- [ ] Реализовать независимый от ESP-IDF C-парсер нужных заголовков и beacon/probe response.
- [ ] Различать исходную длину кадра и доступную длину сохранённого фрагмента.
- [ ] Хранить SSID как байты с длиной; проверять границы каждого IE.
- [ ] Реализовать таблицу 64 AP с ключом BSSID, вытеснением и признаком устаревания.
- [ ] Запустить host-тесты, ASan/UBSan и короткий fuzz-прогон.
- [ ] Добавить CI сборки прошивки и host-тестов, когда эти цели существуют.

Готово, когда обрезанные/повреждённые данные безопасно обрабатываются,
а корректные тестовые beacon дают ожидаемые поля AP.

## M4 — обзор каналов, неделя 4

- [ ] Реализовать `survey`, `monitor`, `paused` и единственного владельца радио.
- [ ] Учитывать реальное время наблюдения; исключить интервалы переключения.
- [ ] Отделить сессию режима от отдельного окна наблюдения канала.
- [ ] Проверить остатки очереди при смене каналов и режимов.
- [ ] Проверить расчёты на синтетических интервалах, включая нулевое время.

Готово, когда данные относятся к своему каналу/окну, а переходы не создают
ложных скоростей и не смешивают старую статистику с новой сессией.

## M5 — законченный интерфейс, неделя 5

- [ ] Добавить экраны каналов, списка AP и выбранной AP.
- [ ] Реализовать команды `survey`, `monitor <channel>`, `pause`, `resume`, `status`, `export on/off`.
- [ ] Передавать агрегаты через UART один раз в секунду; поддержать восстановление host-приёмника после перезапуска.
- [ ] Добавить Python-приёмник с сохранением JSONL и CSV.
- [ ] Проверить работу сбора при ошибке OLED и закрытии программы-приёмника.

После M5 новые функции замораживаются до v1.0. Графики, web UI, PCAP и OTA
не заменяют оставшиеся проверки.

## M6 — испытания, неделя 6

- [ ] Выполнить 100 переключений режимов без зависаний и неожиданных сбросов.
- [ ] Проверить пустой эфир, множество AP, скрытые/непечатаемые SSID и устаревание записей.
- [ ] Проверить неверные команды, длинные входные строки и неполную строку UART.
- [ ] Проверить переполнение очереди и восстановление; сверить учёт записей после остановки/опустошения очереди.
- [ ] Собрать данные по minimum free heap, stack high-water marks и заполнению очередей.

## M7 — измерения, неделя 7

- [ ] Выполнить минимум восемь часов непрерывной работы на реальной плате.
- [ ] Проверить отсутствие неожиданных перезапусков и устойчивого роста занятой памяти.
- [ ] Сравнить спокойный режим своей AP и передачу данных на фиксированном канале.
- [ ] Зафиксировать плату, настройки AP, профиль нагрузки, версию SDK, commit и длительность каждого опыта.
- [ ] Опубликовать результаты с ограничениями: локальные drops не описывают все радиопотери.

Точные throughput и пределы памяти становятся результатами измерений,
а не обещаниями из архитектуры. Сравнение с другим приёмником не требует
равенства счётчиков: условия приёма различаются.

## M8 — оформление, неделя 8

- [ ] Проверить инструкцию на чистой сборке.
- [ ] Добавить фотографии устройства, окончательную схему и видео на 1–2 минуты.
- [ ] Добавить отчёт об испытаниях со ссылками на воспроизводимые сценарии.
- [ ] Выпустить v1.0 только после выполнения обязательных проверок.

В резюме указываются только реализованные функции и фактические результаты.
Формулировка про разработку собственного Wi-Fi/RF-драйвера этому проекту не соответствует.

## Рабочий процесс Git

`main` содержит согласованные небольшие этапы. Для разработки используются
ветки `codex/<task>` при работе агента и `feature/<task>` при самостоятельной работе.
Изменение должно объяснять, какое поведение появилось и как оно проверено.
Не добавлять пустые тесты или зелёные CI-бейджи до появления настоящих проверок.
