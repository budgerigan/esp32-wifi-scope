# Архитектура ESP32 Wi‑Fi Scope

Статус: **проектируемая архитектура**. Прошивка ещё не реализована; поведение,
производительность и совместимость подключения не проверены на плате.
Документ фиксирует границы первой версии и решения для последующей реализации.

## 1. Назначение и ограничения

Устройство наблюдает доступные ему кадры Wi‑Fi 2,4 ГГц и показывает точки доступа,
RSSI и статистику кадров. Это учебный проект на C для портфолио embedded-разработчика.
Он не измеряет весь радиочастотный спектр, точный процент занятости эфира или все потери.

- Платформа: классический ESP32, ESP-IDF **v5.5.6**, C и FreeRTOS.
- Интерфейс: OLED SSD1306 по I²C, две кнопки, USB–UART через мост отладочной платы.
- Радио: `WIFI_MODE_NULL` и promiscuous reception; без подключения к AP и без SoftAP.
- Первая версия принимает кадры пассивно; активное сканирование и передача исключены.
- Фильтры management/data/control и нужных control-subtype задаются явно;
  неизвестные категории и кадры с ошибкой приёма не разбираются как нормальные кадры.
- По умолчанию survey перебирает каналы 1–11 с целевым dwell 250 мс на канал.
- Набор каналов задаётся явно с учётом выбранного региона; UI не меняет его автоматически.
- Вне первой версии: PCAP, веб-интерфейс, SD, OTA, CSI и анализ handshake.

Promiscuous callback вызывается в задаче драйвера Wi‑Fi, **не в ISR**.
Драйвер и радиостек предоставляет Espressif; собственная часть — обработка,
управление режимами, интерфейс и проверяемые ограничения ресурсов.
Источник: [ESP-IDF v5.5.6: Wi‑Fi Driver](https://docs.espressif.com/projects/esp-idf/en/v5.5.6/esp32/api-guides/wifi.html).

## 2. Поток данных и границы модулей

Основной путь: Wi‑Fi callback → фиксированный пул → очередь индексов →
processor → парсер и агрегаты → снимок состояния → OLED / UART → Python CSV collector.

| Модуль | Ответственность | Чего не делает |
| --- | --- | --- |
| `radio` | Инициализация Wi‑Fi, канал, режим, окна наблюдения, callback | Не рисует и не разбирает SSID |
| `capture` | Пул, очереди, перенос копии кадра и локальные счётчики потерь | Не хранит указатели на память драйвера |
| `parser` | Чистый C: проверка границ и нужные поля beacon/probe response | Не зависит от ESP-IDF, RTOS и оборудования |
| `processor` | Единственный владелец таблицы AP и статистики наблюдений | Не вызывает Wi‑Fi API и не ждёт OLED/UART |
| `ui` | OLED через `esp_lcd`, кнопки, отображение снимка | Не меняет таблицу AP напрямую; без LVGL |
| `serial` | Ограниченный набор команд, ответы и JSONL-агрегаты | Не передаёт сырые кадры |
| `host_tools` | Python: приём JSONL и сохранение CSV на компьютере | Не участвует в работе радио |

Названия обозначают будущие компоненты, а не уже существующий код.
В дереве исходников `parser` и `processor` входят в `components/scope_core`,
`capture` — в `scope_capture`, `radio` — в `scope_control`, UI и UART —
в `scope_ui` и `scope_serial`. Адаптер callback расположен в `scope_capture`;
команды Wi-Fi API выполняет только `scope_control`.
Парсер принимает неизменяемый диапазон байтов с явной длиной и возвращает результат
или статус разбора. Его можно собирать и тестировать на компьютере без ESP-IDF.

## 3. Задачи и владение данными

Предусмотрены четыре задачи приложения, кроме служебных задач ESP-IDF:

- **Radio control:** единственный владелец Wi‑Fi API и автомата режимов.
  Принимает команды кнопок/UART и выполняет смену канала по таймеру.
- **Processor:** забирает записи захвата, разбирает их и обновляет AP/статистику.
  Обрабатывает также команды закрытия окна и подтверждает их завершение.
- **UI:** опрашивает кнопки с устранением дребезга, обновляет OLED не чаще 5 Гц.
- **UART:** принимает команды, выдаёт ответы и агрегаты; имеет ограниченные буферы.

Radio control и processor важнее UI/UART по приоритету; конкретные значения
и размеры стеков подбираются после измерения на плате, а не объявляются проверенными.
Все длительные операции экрана и UART происходят вне критических секций.

Пул содержит **64 слота с полезной областью по 512 байт**: 32 КиБ только для копий
кадров. Метаданные, очереди, таблица AP, стеки и память драйвера считаются отдельно.
Каждый слот принадлежит ровно одному из владельцев: free queue, callback,
ready queue или processor. В очередях передаются индексы, а не копии 512 байт.

Callback без ожидания берёт свободный слот, копирует необходимую часть кадра,
записывает метаданные и без ожидания помещает индекс в ready queue.
При отказе постановки он возвращает слот в free queue. Processor возвращает слот
ровно один раз после обработки либо отбрасывания. Обе очереди ограничены 64 индексами.
При нехватке слотов новый кадр отбрасывается; старые записи не перезаписываются.
В горячем пути приложения нет выделения памяти, JSON, логирования или I/O.

Память входного кадра принадлежит драйверу и используется только во время callback.
После возврата callback разрешена работа исключительно с собственной копией.

Processor публикует готовый снимок: режим, AP, статистика, возраст данных и ошибки.
UI/UART копируют его под коротким mutex в свои заранее выделенные буферы,
затем отпускают mutex и выполняют I/O. Processor пропускает публикацию, если mutex занят.
Большие снимки не размещаются как временные массивы на стеке задачи.
Сами AP и агрегаты изменяет только processor, поэтому им отдельный mutex не нужен.

Команды идут в ограниченную очередь radio control. При заполнении возвращается `busy`;
команда не теряется молча. Ответ об успехе выдаётся после фактического перехода.

## 4. Режимы, поколения и окна наблюдения

| Режим | Поведение |
| --- | --- |
| `PAUSED` | Приём в приложение закрыт; UI, команды и последние данные доступны |
| `SURVEY` | Последовательное наблюдение выбранных каналов, по одному в каждый момент |
| `MONITOR` | Непрерывное наблюдение одного канала; можно выбрать AP по BSSID |

После запуска устройство находится в `PAUSED` до завершения инициализации и команды старта.
После успешной инициализации radio control автоматически выполняет старт `SURVEY`;
для автономной работы компьютер не нужен.
Переход через внутреннее состояние `SWITCHING` всегда временно закрывает приём.
При ошибке настройки или тайм-ауте синхронизации устройство остаётся в `PAUSED`
с видимой причиной; оно не продолжает работу с предположительно правильным каналом.

**Поколение режима** (`mode_epoch`) меняется при смене режима, конфигурации,
pause/resume или сбросе статистики. **Окно наблюдения** (`window_id`) меняется
при каждом посещении канала в survey и при новом входе в monitor.
Обычный переход survey на следующий канал не создаёт новое поколение режима.
Внутри monitor периодические UI/JSONL-снимки не закрывают окно и не сбрасывают его.
При новом поколении сбрасываются канальные агрегаты и dwell; общие диагностические
счётчики и таблица AP сохраняются до перезапуска. Пауза замораживает последний снимок,
а `resume` возвращает предыдущий режим/канал с новым поколением статистики.

Активный дескриптор содержит поколение, номер окна, режим, целевой канал,
монотонное время открытия и флаг разрешённого приёма.
Все времена и накопленный dwell — 64-битные микросекунды от монотонных часов;
это не календарное время. Чтение/изменение общего дескриптора и callback-счётчиков
защищены одной короткой критической секцией; на 32-битном ESP32 нельзя считать
несинхронизированное чтение 64-битного значения атомарным.

Для каждого принятого кадра сохраняются `mode_epoch`, `window_id`, время callback,
фактический `rx_channel`, RSSI, тип кадра, исходная и скопированная длины.
Время callback — программная отметка приёма приложением, не точное время в эфире.
Тип и границы SDK-пакета проверяются до обращения к payload; неизвестный тип
не интерпретируется как обычный management/data/control кадр.

## 5. Безопасное переключение канала

Для первой версии выбран простой консервативный порядок:

1. Radio control под короткой критической секцией закрывает gate приёма
   и фиксирует время закрытия текущего окна.
2. Отключает promiscuous reception и ждёт завершения callback, уже допущенных
   через gate. Для этого callback ведёт счётчик `in_flight` под той же защитой.
   Ожидание происходит вне критической секции и имеет тайм-аут.
3. Processor завершает уже начатую обработку, **отбрасывает оставшуюся ready queue**,
   возвращает слоты и увеличивает `transition_discard`. Затем закрывает окно
   с переданным временем и подтверждает границу. Это осознанная потеря приложения.
4. Radio control меняет режим/канал, проверяет результат API и запускает приём
   при ещё закрытом gate. Processor получает описание нового окна и подтверждает
   готовность. Только после этого radio control публикует время открытия в общем
   дескрипторе и открывает gate. Неуспех любого шага оставляет устройство в `PAUSED`.

Callback, увидевший закрытый gate, не получает слот и увеличивает `boundary_rejected`.
Допущенный callback увеличивает `in_flight` до выхода из критической секции;
уменьшает его на любом пути завершения. Отключение драйвера само по себе
не считается доказательством отсутствия callback, уже выполняющихся приложением.
Processor не подтверждает границу, пока очередь не пуста и все её слоты не возвращены.

Данные старого поколения/окна никогда не попадают в новое. Защитная проверка processor
отбрасывает несоответствие с отдельным счётчиком `stale_record`.
Запись с `rx_channel`, отличным от канала её окна, не участвует в статистике окна;
для неё есть `channel_mismatch`. Глобальная переменная «текущий канал» не заменяет
метаданные уже принятой записи.

Dwell — фактическая длительность открытого gate, а не установленный таймер 250 мс.
Переключение, синхронизация и пауза не входят в dwell. Счётчики окна увеличиваются
только по обработанным записям; отброшенный остаток очереди делает наблюдение неполным.
Для текущего незакрытого окна снимок учитывает время от открытия до момента снимка;
для закрытых окон берётся зафиксированная длительность, без повторного суммирования.
Программная граница не обещает точной границы RF-приёма внутри закрытого драйвера.

## 6. Парсер и таблица точек доступа

Подробно разбираются только beacon и probe response: минимальный заголовок,
фиксированные поля и ограниченный обход Information Elements для SSID/канала.
Management/data/control считаются отдельно; payload пользовательских данных не разбирается.

- `captured_len` всегда ограничивает чтение, даже если `original_len` больше.
- Адаптер SDK нормализует границу 802.11-кадра и FCS до вызова чистого парсера;
  формат длины проверяется по заголовкам закреплённой версии SDK и на тестовом кадре.
  FCS не должен интерпретироваться как ещё один Information Element.
- `truncated` означает недостаток скопированных байтов; `malformed` — структурное
  нарушение, доказуемое в доступной части. Эти причины не смешиваются.
- Поле учитывается только если целиком попало в копию; наличие первых полей
  не означает, что полный кадр проверен. Обрезанный хвост не превращается в пустой SSID.
- SSID хранится как до 32 байт и отдельная длина, без предположения о завершающем нуле.
  Hidden SSID, произвольные байты и невалидный UTF-8 допустимы как входные данные.
- OLED получает безопасное печатное представление; JSON экранируется и может
  передавать SSID в hex для сохранения точных байтов без догадок о кодировке.

Таблица ограничена **64 AP**, ключ — BSSID. Новая AP занимает свободную запись,
иначе вытесняет запись с самым старым `last_seen`; вытеснения считаются отдельно.
Смена режима не удаляет таблицу, но возраст наблюдений всегда виден; перезапуск удаляет её.
Через 30 секунд без наблюдения AP помечается устаревшей; RSSI не заменяется нулём.
Выбор AP хранится по BSSID, а не по индексу, который может быть переиспользован.

`rx_channel` — канал фактического наблюдения из SDK-метаданных.
`advertised_channel` — объявленный самой AP канал, если поле удалось разобрать.
Отсутствие или конфликт объявленных данных показываются как unknown/conflict;
они не заменяют `rx_channel` и не меняют канал статистики задним числом.
Автоматический переход к AP разрешён только при известном непротиворечивом
объявленном канале из настроенного набора. Иначе UI предлагает выбрать канал вручную.
RSSI выбранной AP в первой версии обновляется по её beacon/probe response,
а не по произвольно приписанным ей data/control кадрам.

## 7. Метрики и проверка архитектуры

Для каждого канала доступны observed management/data/control frames,
суммарный dwell, frames/s = обработанные кадры / dwell и возраст последнего окна.
Bytes/s считается по исходной длине успешно учтённых кадров из SDK, включая FCS,
а не по длине сохранённых 512-байтных фрагментов. При нулевом dwell скорость
отсутствует (`null` в телеметрии), а не равна нулю или бесконечности.
Показатели разных каналов получены последовательно; UI не изображает их одновременными.
RSSI показывается только по реально полученным наблюдениям, без заполнения пропусков нулями.

Отдельно видны `pool_exhausted`, `enqueue_failed`, `transition_discard`,
`boundary_rejected`, `channel_mismatch`, `stale_record`, `truncated`, `malformed`
и AP evictions. Отбрасывания по разным причинам не считаются дважды;
truncated/malformed — диагностические признаки, а не автоматически потерянные кадры.
Потери внутри радио/драйвера и кадры, пропущенные вне наблюдаемого канала, неизвестны.
Локальные счётчики нельзя называть общим процентом потерь эфира.
Отдельно передаются uptime, minimum free heap, stack high-water marks,
максимальное заполнение очереди и `export_dropped` для пропущенных снимков UART.
Телеметрия имеет версию формата и идентификатор загрузки; host-приёмник отделяет
перезапуски и игнорирует загрузочные строки, не являющиеся JSON. Медленный UART
пропускает снимок с увеличением счётчика, но не задерживает processor/radio control.

Проверки реализации: host-тесты парсера с ASan/UBSan и короткий fuzz-прогон;
искусственное заполнение очереди; смена канала при непустой очереди и активном callback;
проверка окна/поколения и суммы времени при pause/resume; 100 смен режимов;
8-часовой прогон с heap/stack high-water telemetry и собственной AP в idle/busy.
До этих испытаний параметры пула, dwell и частоты UI — проектные настройки,
а не подтверждённые характеристики готового устройства.
